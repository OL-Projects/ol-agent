Default vs. verifiable

Two kinds of agents.

Same task, same model, same afternoon. The difference is what happens after the output exists.

The defaultGenerates

  • It writes something shaped like the finished thing.
  • It sounds exactly as sure when it is wrong.
  • It reports success because a request returned 200.
  • It cannot tell you how it knows.
  • It hands you the risk.

The verifiable agentActs, then proves

  • It renders the document and measures the pixels.
  • It recomputes the total before it prints it.
  • It compares the bytes served to the bytes built.
  • It records the tier it reached, not the one it hoped for.
  • It hands you the evidence.

One hands you output. The other hands you output and the receipt.

3 checks · real thresholds

Nothing leavesuntil it passes.

Between the work and you sits a gate. Each kind of output has a verifier that knows what wrong looks like. If any check fails, the output is refused, the reason is written down, and the unit stays open.

  1. 01

    Rendered to pixels

    Every page of a document is rendered to PNG and measured before it may leave.

    Passclipping = 0 px · ink > 0 on every page
  2. 02

    Arithmetic recomputed

    Subtotal plus GST 5% plus QST 9.975% is recomputed and compared to the printed total.

    Pass|printed − recomputed| < $0.01
  3. 03

    Bytes, not status codes

    A static deploy is accepted only when the bytes served hash-match the bytes built. A 200 alone is not accepted.

    Passsha256(served) = sha256(built)

The limit, statedA verifier proves what it measures. It proves the total adds up. It does not prove the invoice went to the right client. That question is still yours.

Why this section exists

A product that asks you to check its work cannot begin by asking you to believe a web page. So this page is made of the same rule it sells: publish the hash, let anyone recompute it, and print the result whether or not it flatters us.

The limit, statedA hash proves the bytes you received are the bytes that were built. It does not prove the bytes are any good. One of those is measurable. The other is still your judgement.

Same rule in the repository: proof.py --check recomputes every hash on each push and fails the deploy if one line disagrees. The page cannot go live with a stale receipt.
